# コード用語説明ポリシー

このドキュメントは、複数の背景を持つ参加者（特にコード初心者）が共通で理解できるよう、
テクニカル用語を説明する方法を定めます。

---

## 目的

- 複雑なテクニカル用語をシンプルに説明する
- コード初心者も上級者も同じドキュメントから学べる
- AI も統一された説明方法を使用する

---

## 基本ルール

### ルール 1: 最初の登場時に必ず説明する

ドキュメント、コード、Issue で **初めて出現するテクニカル用語** には、以下の構造で説明を加えてください。

```markdown
**【用語】** [テクニカル用語]
**【簡潔な説明】** [1 文で、分かりやすく]
**【別の言い方】** [同義語、比喩、日本語訳]
**【図解またはコード例】** [視覚的な説明]
**【メリット・理由】** [なぜ使うのか]
**【注意点】** [ハマりやすいポイント]
```

### ルール 2: 対象ユーザーで説明方法を使い分ける

- **コード初心者向け**: 日常用語や比喩を使う
- **上級者向け**: 技術的な詳細を含める
- **双方向対応**: 簡潔な説明と詳細な説明を分ける

### ルール 3: 不要な専門用語を避ける

```markdown
❌ 駄目な例：
「Async/await パラダイムにより、Promise チェーンを簡潔に記述できます」

✅ 良い例：
「通常、複数の処理を順番に実行するときは、ネストが深くなります。
async/await は『ネストを減らし、読みやすくする方法』です。
イメージ：階段（ネスト）を降りるのではなく、平坦な道を歩く感じ」
```

## 説明テンプレート

### パターン 1: 単純な概念

```markdown
**【用語】** TypeScript

**【簡潔な説明】** 
JavaScript に「データの型（種類）を事前に指定する機能」をつけたもの

**【別の言い方】** 
- 「型安全な JavaScript」
- 「品質管理機能付き JavaScript」

**【例】**
```javascript
// ❌ JavaScript（何でも入る）
let user = "太郎";
user = 123;  // エラーにならない

// ✅ TypeScript（型を指定）
let user: string = "太郎";
user = 123;  // エラー！「文字列が入る箱に数字を入れられない」
```

**【メリット】** 
バグを早期に見つけられます。本番環境でバグが発生する前に、開発時点で「型が違う」エラーが出ます

**【注意点】**
最初は「型を指定する作業」が手間に感じるかもしれませんが、
バグを減らす投資だと考えてください
```

### パターン 2: 複雑な概念（段階的説明）

```markdown
**【用語】** API（Application Programming Interface）

**【レベル 1：簡潔な説明】** 
「アプリケーション同士が会話するための『決まった方法』」

**【レベル 2：具体例】** 
例）天気アプリが気象サービスに「〇〇の天気を教えて」と聞く方法。
- 「決まった方法」 = HTTP GET, POST などのルール
- 「決まった形式」 = JSON というデータ形式

**【レベル 3：技術詳細】** 
REST API の例）
```
GET /api/weather?city=tokyo
→ 気象サービスが JSON 形式で返す：
{
  "city": "Tokyo",
  "temperature": 25,
  "condition": "Sunny"
}
```

**【メリット】** 
- 異なるプログラミング言語・プラットフォーム間でデータ交換できる
- アプリケーション同士が協力して複雑な処理を実現

**【注意点】** 
- API は「約束」なので、クライアント・サーバー双方が約束を守る必要がある
- 仕様が変わるとクライアント側も修正が必要
```

### パターン 3: 設計・アーキテクチャ用語

```markdown
**【用語】** MVVM（Model-View-ViewModel）

**【簡潔な説明】** 
アプリケーションを 3 つの層に分ける設計パターン

**【レイヤー説明】**

| 層 | 役割 | イメージ |
|-----|------|--------|
| **Model** | データを管理 | 「本当の情報」（ユーザー名、年齢など） |
| **View** | 画面に表示 | 「テレビの画面」（データがどう見えるか） |
| **ViewModel** | Model と View をつなぐ | 「テレビのリモコン」（Model の変更を View に通知） |

**【図解】**
```
User（ユーザー）
  ↓（操作）
View（画面）← ViewModel（橋渡し）→ Model（データ）
  ↑（表示更新）
```

**【メリット】** 
- 役割が明確で、バグを見つけやすい
- 各層を独立してテストできる
- チーム開発で分業しやすい

**【注意点】** 
- ViewModel の責任が大きくなりすぎないか監視（肥大化を避ける）
- 小規模プロジェクトではオーバーキルな場合も
```

## 説明が必要な場面

### 必ず説明する

- [ ] 初めて出現するテクニカル用語
- [ ] プロジェクト固有の造語（例：「RecipeExecutionResult」）
- [ ] 複数の意味で使われる用語（例：「Model」は MVC の Model、データベースの Model など）
- [ ] エラーメッセージの用語（例：「TS2339」エラーの説明）

### コンテキストが明確なら省略可

- [ ] 既に説明済みの用語（同じドキュメント内で）
- [ ] 非常に一般的な用語（例：「ファイル」「フォルダ」）
- [ ] コード側のコメントで説明済み

## AI への指示テンプレート

複数の AI に「コード初心者向けに説明する」と指示する場合：

```markdown
【依頼】
上記のコードを実装してください。
コード用語は「CODE_TERMINOLOGY.md」のポリシーに従って説明してください。

【具体的に】
- テクニカル用語の初登場時に説明を追加
- 初心者にも理解できる比喩・図解を含める
- ハマりやすいポイントを記載

【例：説明が必要な用語】
- TypeScript 型定義
- async/await
- Promise
- API endpoint
- データ構造
```

## よくある用語と説明例

### 1. TypeScript 型定義

```markdown
**【用語】** TypeScript の型定義（型アノテーション）

**【簡潔な説明】**
「この変数には、この種類のデータが入ります」と事前に宣言すること

**【比喩】**
- 郵便物の仕分け：「この箱は手紙用」「この箱は小包用」と決めておく
- 駅の改札：「ICカード専用」「現金専用」と決めておく

**【コード例】**
```typescript
// ❌ 型定義なし（何でも入る）
let age = 25;

// ✅ 型定義あり（数字のみ）
let age: number = 25;

// ❌ これはエラー
age = "twenty five";  // 「数字の箱に文字を入れられない」
```

**【メリット】**
バグを事前に発見できます。本番環境でバグが出る前に、開発時点でエラーが出ます

**【注意点】**
最初は手間に感じるかもしれませんが、大規模プロジェクトではバグを劇的に減らせます
```

### 2. async/await

```markdown
**【用語】** async/await（非同期処理）

**【簡潔な説明】**
「時間がかかる処理（例：データベースの読み込み）を待つ間に、他の処理も実行する」仕組み

**【比喩】**
レストランの例：
- ❌ 同期的：お客さんが「ラーメン」と注文 → 完成まで立ったまま待つ
- ✅ 非同期的：お客さんが「ラーメン」と注文 → 席に座る → 番号を受け取る → 完成まで他のお客さんの対応 → 番号が呼ばれたら提供

**【コード例】**
```typescript
// ❌ 何もしないまま待つ（効率が悪い）
const userData = fetchUserData();  // 5 秒待つ
console.log(userData);

// ✅ 待っている間に他も実行（効率が良い）
const userData = await fetchUserData();  // 5 秒かかるが、その間に他の処理も実行
console.log(userData);
```

**【メリット】**
ウェブアプリが快適に動く。ユーザーが「画面が止まった」と感じません

**【注意点】**
複数の非同期処理が絡むと複雑になり、バグが生まれやすい
```

### 3. API Endpoint

```markdown
**【用語】** API Endpoint（API の入口）

**【簡潔な説明】**
「アプリケーションが外部と通信するための『住所』のようなもの」

**【比喩】**
- 郵便の例：〒100-0001 東京都 千代田区... = endpoint
- ウェブサイト：https://example.com/api/users = endpoint

**【コード例】**
```
GET /api/users
→ 全ユーザーの一覧を取得

GET /api/users/123
→ ID 123 のユーザー情報を取得

POST /api/users
→ 新しいユーザーを作成

DELETE /api/users/123
→ ID 123 のユーザーを削除
```

**【メリット】**
フロントエンド（画面）とバックエンド（サーバー）が統一された方法で通信できます

**【注意点】**
endpoint の設計が悪いと、クライアント側で複雑な処理が必要になります
```

### 4. Promise

```markdown
**【用語】** Promise（約束）

**【簡潔な説明】**
「将来「成功」するか「失敗」するかわからない非同期処理」を表すオブジェクト

**【比喩】**
お医者さんの予約：
- 「今日の 15 時に来てください」 = Promise
- 待機中 = pending（待機中）
- 15 時に患者が来た = resolved（成功）
- 患者がキャンセルした = rejected（失敗）

**【ステータス】**
```
Pending（待機中） → Resolved（成功） → データを利用
                  ↓
                Rejected（失敗） → エラーを処理
```

**【注意点】**
Promise チェーンが深くなると読みにくくなる（コールバック地獄）
→ そのため async/await が登場
```

## Documentation の中での使用方法

### GitHub で

PR や Issue に複雑な用語が出た場合：

```markdown
## 実装内容

**【新規追加】** Authentication middleware（認証ミドルウェア）

**【説明】**
リクエストが API に到達する前に、ユーザーが本当に認証されているか確認する機能です。

イメージ：
```
Request（リクエスト）
  ↓
Authentication Middleware（本人確認）「あなた誰ですか？」
  ↓ OK なら
API Endpoint へ
```

【技術詳細】
- JWT トークンをチェック
- 有効期限を確認
- 権限を確認
```

### Obsidian で

実装記録に用語説明を含める：

```markdown
# [機能] 実装記録

## 使用した技術

### async/await（非同期処理）
複数のデータベースクエリを並列実行するため使用。
Promise チェーンより読みやすく、バグが少ない。

詳細：GitHub CODE_TERMINOLOGY.md 参照
```

## 改善と更新

このポリシーは、以下の場合に改善します。

- ユーザーが「この用語が理解できなかった」と報告
- 繰り返し説明が必要になる用語が増えた
- 新しい技術が採用され、説明方法が必要になった

改善案があれば、Issue を作成してください。

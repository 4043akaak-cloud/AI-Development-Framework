# 開発フロー

この文書は、人間と複数の AI が同じリポジトリで作業するときの基本的な進め方を定めます。

共通ルールの正本は `guidelines/AI_COLLABORATION.md` です。この文書では、そのルールを実際の作業手順にします。

## 基本原則

- 目的と完了条件を確認してから変更する
- 影響の大きい判断は、人間が承認する
- 変更は小さな単位に分け、検証結果を残す
- 作業の区切りでは、次の人間または AI が続けられる情報を残す

## 全体の流れ

```text
依頼の確認
  → 文脈の確認
  → 方針の提案・合意
  → 実装または文書更新
  → 検証
  → 結果の報告・引き継ぎ
  → 人間のレビュー・コミット・マージ
```

## 1. 依頼の確認

作業を始める前に、依頼から次の内容を確認します。

- 解決したい課題と目的
- 完了とみなす条件
- 変更してよい範囲と、変更してはいけない範囲
- 期限、優先順位、特別な制約

内容が不明確で、実装や設計の方向が変わる場合は、人間に確認します。

## 2. 文脈の確認

作業に着手する AI は、次を確認します。

1. `README.md`
2. `docs/project/PROJECT.md`
3. `guidelines/AI_COLLABORATION.md`
4. 関連する設計・決定記録・既存の実装
5. 現在の変更状況と、他の参加者が進めている作業

確認した情報だけでは判断できない場合は、前提を明示し、人間に質問するか、影響のない範囲に作業を限定します。

## 3. 方針の提案と合意

複数の方法がある場合、AI は推奨する方針と理由を示します。必要に応じて、代替案、影響範囲、リスク、検証方法も示します。

次の内容は、実行前に人間の承認を得ます。

- 目的・要件・対象範囲の変更
- 互換性、セキュリティ、公開範囲、費用、権限に影響する変更
- データの削除や移行
- 外部サービスへの送信・公開

## 4. 実装または文書更新

- 目的に直接関係する最小限の変更を行う
- 無関係なリファクタリングや仕様変更を混ぜない
- 既存のルールや他者の変更を、確認なく上書き・削除しない
- 重要な判断をした場合は、決定記録の追加または追加提案を行う

現時点では、ブランチ、Issue、プルリクエストの具体的な運用は未決定です。運用が決まるまでは、人間の指示に従います。

## 5. 検証

変更に応じて、適切な検証を実施します。

| 変更の種類 | 確認例 |
| --- | --- |
| ドキュメント | 内容の整合性、リンク・パス、Markdown 表示 |
| 設定 | 構文確認、影響範囲の確認 |
| コード | テスト、静的解析、ビルド、動作確認 |
| 設計・運用ルール | 既存文書との矛盾、実行可能性、人間のレビュー |

実行できなかった検証は、理由とともに「未検証」と報告します。

## 6. 結果の報告と引き継ぎ

作業を終えた AI は、次の内容を簡潔に報告します。

- 実施した変更と目的
- 変更したファイル
- 実施した検証と結果
- 未検証事項、残る懸念、未解決の課題
- 次に行う作業、または人間に必要な判断

別の AI が続けて作業する場合も、この報告を引き継ぎ情報として利用します。

## 7. 人間によるレビューと記録

人間は、目的と完了条件に照らして変更内容を確認し、コミット、マージ、公開などの最終判断を行います。

重要な設計・運用判断を確定した場合は、今後 `docs/decisions/` に決定内容、背景、選択肢、影響を記録します。

## フローの改善

このフローで手戻りや不明確さが生じた場合は、原因と改善案を共有し、人間の確認後に更新します。

# ADF Goal

## Goal

人間が司令塔として使える、**AIRFLOW型の可視化**と**ループコーディング**を統合したAI開発運用アプリをつくる。

このアプリは、複数プロジェクト・Task・担当AI・承認待ち・リスクを一画面で見渡し、`観測 → Context → Plan → Approval → Implementation → Verification → Review → 学び → 次Task`の開発ループを、根拠を失わず回せるようにする。

GitHubはTask・実装・検証の正本、Obsidianは背景・判断理由・長い調査の正本として維持する。アプリは両者を置き換えず、人間が判断するための司令塔になる。

将来の複数AI管制は、司令塔（Control Plane）、隔離された作業（Work Plane）、根拠と統合判断（Evidence Plane）を分ける。AIの数を増やすことではなく、人間承認と正本に戻れるEvidenceを失わずに、役割ごとの成果物を比較・統合できることを目標にする。

## MVP Goal（current）

現在のMVPのゴールは、このPC内に「AI同士が、プロジェクトを完遂するために議論し、結果を受け渡す場所」を作ることである。

対象は次の2点に限定する。

1. ADFの実行環境はこのPC内のローカル運用とする。
2. ADFの目的は、管理対象プロジェクトの完遂に必要な進捗管理とAI間の受け渡しに限る。

最小の成立ループは、Project Ownerの依頼 → 承認済みTask → ローカルJob → 役割を持つ複数AIの議論 → 構造化Result → Ownerレビュー／次Task、である。現在はFake Adapterでこの議論を成立させ、後から実AI Adapterを差し替えられる土台を作る。

ADF自身がプロジェクト固有の分析を行うこと、万能なAI実行基盤になること、クラウドサービスになることはMVPのゴールに含めない。Claude API/CLIなどの外部接続、外部送信、課金、外部正本の自動変更は、ローカルMVP成立後の別Task・別承認とする。

## 成功条件

- Project Ownerが、複数プロジェクトの目的、現在地、承認待ち、リスク、次に必要な判断を一画面で確認できる。
- 各Taskが、Contextから学び・次Taskまでのループを飛ばさず、根拠と停止条件を確認できる。
- 上司AI、実装AI、レビューAIを増やしても、役割・権限・承認境界が可視化される。
- 新しいAIを加える場合も、接続方式、データ送信、費用、停止、出力契約を人間が確認・承認できる。
- AI固有の会話履歴・Memory・IDEだけに、作業継続に必須の情報が残らない。

## 現在の優先順位

最初にこのPC内で、Fake Adapterを使った複数AIの議論とOwnerレビューまでの最小ループを検証する。次に、同じ契約を保ったまま実AI Adapterを別Taskとして接続する。自動選定、クラウド運用、汎用的なAI実行基盤化は、現在のMVP完遂後も必要性と実測を確認してから扱う。
